Obnovení a převod firemního webu

Jednoduchý návod pro majitele webu a jeho případného nového správce. Obsahuje dvě nezávislé možnosti obnovení: s GitHubem a Cloudflare nebo na běžném webhostingu bez těchto služeb.

Web: https://vodotopokobliha.cz/
Typ: statický web bez databáze a bez WordPressu
Registrátor domény: FORPSI (registrace domény nemusí být při stěhování měněna)
Současné DNS: Cloudflare · E-mail: Seznam Email Profi

Co tato záloha zajišťuje: Z webových souborů v přiloženém archivu může jiný správce znovu zveřejnit shodný obsah a vzhled webu. Není nutné získat přístup do původního účtu GitHub ani Cloudflare. K použití domény vodotopokobliha.cz ale musí mít majitel možnost měnit její DNS/NSSET u registrátora.

1. Co obsahuje ZIP

Stažený archiv obsahuje složku s kompletními zdrojovými soubory webu a tuto příručku ve složce PREDANI. Základní struktura:

Soubor / složkaÚčel
index.htmlHlavní stránka, texty, vzhled i základní SEO nastavení.
assets/Grafika a optimalizované fotografie. Zachovat celou strukturu.
favicon.svg, apple-touch-icon.pngIkony webu.
robots.txt, sitemap.xmlSoubory pro vyhledávače.
_headersNastavení HTTP hlaviček pro Cloudflare Pages; na jiném hostingu se automaticky nemusí použít.
README.md, TODO.md, .github/, další .md a scripts/Technická dokumentace a vývojové soubory. Jsou užitečné novému správci; na obyčejný hosting se běžně nenahrávají.
PREDANI/NAVOD_OBNOVENI_WEBU.htmlTato příručka. Lze otevřít v prohlížeči a vytisknout pomocí Ctrl+P.
Záloha neobsahuje: hesla, přístupy do FORPSI/GitHubu/Cloudflare, privátní DNSSEC klíče, historii e-mailových schránek ani konfiguraci DNS zóny z účtu Cloudflare. Tyto věci se při migraci řeší samostatně. Celý ZIP nevkládejte na veřejný webhosting. Zveřejnit se mají pouze soubory určené pro web.

2. Co připravit před jakýmkoli přesunem

  1. Ověřit kontrolu nad doménou: majitel nebo jeho pověřený správce se musí dostat do správy domény u FORPSI a mít právo měnit NSSET, KEYSET a DNS podle potřeby.
  2. Rozhodnout, kdo bude správcem: nového hostingu, domény a případně GitHubu a Cloudflare. U nové infrastruktury doporučujeme účty založené na firmu a správci přidělit jen potřebná oprávnění.
  3. Připravit zálohu DNS: pokud je současná DNS zóna ještě dostupná, vypsat nebo exportovat všechny záznamy, zejména A/AAAA/CNAME, MX, TXT (SPF), DKIM, DMARC, případně CAA a další používané záznamy. V archivu webu tyto záznamy nejsou.
  4. Nechat starý web běžet: nový web nejprve otestovat na dočasné adrese. DNS přepínat až po úspěšném testu.
  5. Zapsat původní stav: který hosting obsluhuje doménu, aktuální NSSET a KEYSET u CZ.NIC, kam směřuje pošta a jaká přesměrování fungují.
Varianta A

GitHub ukládá zdrojové soubory. Cloudflare Pages web automaticky zveřejňuje. Vhodná pro správce, kteří chtějí verzování a snadný návrat k předchozí verzi.

Varianta B

Soubory se uloží přímo u běžného poskytovatele webhostingu. GitHub ani Cloudflare nejsou potřeba. Vhodná pro jednoduché předání jinému správci.

3. Varianta A – obnovení pomocí GitHubu a Cloudflare

Potřebujete: přístup k novému účtu GitHub, Cloudflare a k doméně u FORPSI. Není potřeba účet původního dodavatele.

  1. Rozbalit ZIP do samostatné složky v počítači. Ověřit, že se uvnitř nachází index.html a assets/.
  2. Vytvořit vlastní GitHub repozitář (například vodo-topo-kobliha). Pomocí GitHub Desktop nebo Git nahrát zdrojové soubory ze ZIPu do nové větve main. Pohlídat strukturu – index.html musí být v kořenovém adresáři repozitáře, nikoli v další vnořené složce.
  3. V Cloudflare otevřít Workers & Pages, vytvořit nový projekt typu Pages, zvolit připojení existujícího GitHub repozitáře a vybrat nově vytvořený repozitář.
  4. Nastavit statický web: produkční větev main; bez frameworku; build není potřebný (podle aktuálního rozhraní lze použít příkaz exit 0); výstupní adresář ., pokud je index.html v kořeni projektu. Konfiguraci před nasazením ověřit podle aktuální dokumentace Cloudflare.
  5. Otestovat adresu přidělenou v doméně *.pages.dev. Projít hlavní stránku, mobilní vzhled, všech šest referencí, ikonky a telefonní/e-mailové odkazy.
  6. Připojit vlastní doménu v nastavení projektu Pages. Pokud nová instalace používá i nový účet Cloudflare pro DNS, napřed připravit všechny DNS záznamy v nové zóně a řídit se postupem v kapitole 5. Samotné přidání domény v Pages není bezpečný pokyn k okamžité výměně nameserverů.
  7. Po přepnutí DNS ověřit HTTPS, přesměrování HTTP a www, DNSSEC i funkci firemní pošty. Původní hosting zatím nerušit.
Důležité: Pokud se pouze přesouvají zdrojové soubory a Pages projekt v rámci stejného účtu Cloudflare, nemusí být nutné měnit DNSSEC nebo autoritativní DNS. Pokud se ale web i DNS stěhují do jiného účtu Cloudflare, mohou se změnit nameservery i DNSSEC klíče. To už je změna DNS poskytovatele a vyžaduje kapitolu 5.

Oficiální návod: Cloudflare Pages – Static HTML.

4. Varianta B – běžný hosting bez GitHubu a Cloudflare

Potřebujete: běžný webhosting podporující statické HTML soubory a HTTPS (například hosting u FORPSI nebo jiného poskytovatele), přístup k jeho správě a kontrolu nad doménou.

  1. Objednat běžný webhosting pro doménu vodotopokobliha.cz. Není potřeba WordPress ani databáze; web je tvořen statickými soubory.
  2. Rozbalit ZIP a do veřejného kořenového adresáře hostingu (například www, public_html nebo htdocs) nahrát index.html, celou složku assets/, favicon.svg, apple-touch-icon.png, robots.txt a sitemap.xml. Zachovat názvy i relativní cesty.
  3. Nenahrávat vývojové podklady jako .github/, scripts/, README.md, TODO.md či složku PREDANI/ do veřejného adresáře hostingu. Ponechat si je soukromě jako technickou zálohu.
  4. Nastavit HTTPS s platným certifikátem pro doménu a případně www. Obvykle lze zapnout bezplatný certifikát v administraci webhostingu.
  5. Nastavit přesměrování: http://vodotopokobliha.cz/, http://www.vodotopokobliha.cz/ i https://www.vodotopokobliha.cz/ mají trvale (HTTP 301) vést na https://vodotopokobliha.cz/. Způsob nastavení záleží na hostingu.
  6. Otestovat web před přepnutím DNS na testovací adrese nebo přes funkci náhledu hostingu. Zkontrolovat všechny obrázky, strukturu stránky, telefonní a e-mailové odkazy.
  7. Pokud odcházíte i z Cloudflare DNS: zřídit autoritativní DNS u nového poskytovatele, přesně do něj převést veškeré potřebné DNS záznamy, a teprve potom postupovat podle kapitoly 5. Pokud Cloudflare nadále zůstává DNS správcem, mění se pouze DNS záznamy webu a DNSSEC/NSSET se nemění.
  8. Po přepnutí domény znovu otestovat HTTPS, přesměrování, DNSSEC a e-mail. Zkontrolovat i to, zda nový hosting umí bezpečnostní HTTP hlavičky; původní soubor _headers funguje specificky na Cloudflare Pages.
Důležité oddělení: Přestěhování webhostingu samo o sobě neznamená přestěhování registrace domény nebo e-mailových schránek. Doména může zůstat u FORPSI a e-mail dále u Seznam Email Profi.

5. DNSSEC a bezpečné přepnutí DNS – nejcitlivější část

V říjnu 2026 je pro vodotopokobliha.cz aktivní DNSSEC s KEYSETem KOBLIHA-CLOUDFLARE-DNSSEC, který odpovídá klíčům stávajících DNS serverů Cloudflare. Tyto konkrétní klíče nelze automaticky přenést na jiného DNS provozovatele.

Varování: Pokud správce změní nameservery a nechá v registru CZ.NIC starý DS/KEYSET pro původní Cloudflare klíče, může validace DNSSEC selhat (SERVFAIL). Výsledkem může být nedostupný web i e-mail, přestože jsou jejich servery v pořádku. Neprovádějte změnu NSSET a KEYSET metodou pokus–omyl.

Bezpečná běžná varianta: vypnutí DNSSEC během migrace DNS

  1. Nejprve připravit nového DNS poskytovatele: u nových autoritativních serverů založit všechny nutné záznamy a ověřit, že je servery správně vracejí; zejména MX a TXT pro Seznam Email Profi. Staré DNS musí zatím zůstat aktivní.
  2. Ve FORPSI odebrat přiřazení původního KEYSETu k doméně (tj. zajistit odstranění starého DS z nadřazené zóny .cz). Změnu musí provést oprávněný správce podle aktuálního postupu registrátora.
  3. Vyčkat nejen na veřejné odstranění DS u CZ.NIC, ale i na vypršení jeho TTL v cache validujících resolverů. Nestačí, že na jedné obrazovce již DS není; délka čekání záleží na skutečném TTL.
  4. Teprve potom změnit NSSET / nameservery na nového DNS poskytovatele. Nechat původní i nové DNS dostupné po přechodnou dobu a kontrolovat odpovědi.
  5. Až nový DNS funguje, znovu zapnout DNSSEC, pokud jej nový poskytovatel podporuje, a vytvořit/registrovat odpovídající nový KEYSET/DS. Pokud nový poskytovatel DNSSEC neumí, lze mít funkční doménu bez DNSSEC; zabezpečení DNS však bude nižší.
  6. Ověřit plnou validaci proti autoritativním serverům a nezávislým validujícím resolverům, nikoliv jen přítomnost DNSKEY/RRSIG.

Pokročilé bezvýpadkové přechody s multi-signer DNSSEC existují, ale vyžadují podporu obou DNS provozovatelů a odbornou koordinaci; tento jednoduchý návod je nenahrazuje.

Kontroly: Verisign DNSSEC Debugger, Internet.nl. Pro správu .cz používat FORPSI a informace registru CZ.NIC.

7. Jak se web po převodu aktualizuje

Pokud používáte GitHub + Cloudflare

Správce upraví index.html nebo obrázky v assets/, uloží změnu do repozitáře a Cloudflare Pages obvykle automaticky vytvoří nové nasazení. Po změně je třeba ověřit úspěšný deployment a stránku na mobilu i počítači.

Pokud používáte běžný webhosting

Správce upraví soubory v počítači a nahraje změněné soubory přes správce souborů hostingu nebo bezpečné SFTP/FTPS. Na běžném hostingu se obvykle používá ruční zveřejnění. Před každou úpravou se doporučuje zachovat kopii předchozí funkční verze.

Co zvládne majitel sám

Pan Kobliha může připravit nové texty, opravy kontaktů a fotografie a předat je vybranému správci. Současný web nemá redakční systém pro klikací úpravy. Změny lze technicky dělat bez původního dodavatele, ale je vhodné, aby je provedl člověk znalý práce s HTML a hostingem.

Jistota nezávislosti: archiv webu a tento návod umožňují zvolit nového správce. Majitel by si měl samostatně uchovávat přístupy ke své doméně a novým provozním účtům. ZIP si bezpečně uschovejte a po větších změnách vytvořte novou kopii.
